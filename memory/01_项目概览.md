# 01 项目概览

> 最后核对：2026-11-25（整理 memory base：写入 11-22 的 Boss 第 0～4 阶段；文件夹结构按用户 11-22 的改名：`Player_V0.2` → `Player_V0.3`，`Enemies` → `Boss`）

## 基本信息

- **类型**：2D 动作平台游戏（近战连招 + 远程射击 + 飞行 + Boss 弹幕战）
- **主角**：芙兰（Flandre），代码命名空间 `Flandre.CombatSystem`
- **引擎**：Unity `6000.3.1f1`
- **规模**：约 146 个 C# 脚本、约 2 万行（玩家约 1.15 万行，Boss/敌人约 5.5 千行）
- **仓库**：`https://github.com/Diaomao-Pmz/Flan`，本地 `D:\Unity project\Flan`

## 和用户协作的规矩（2026-11-21 总结，11-22 补充）

- **改文件前先说明**：先从功能角度说这次要实现什么，再说代码怎么改、改哪些文件；**等用户确认后再动手**。改完列出每个文件的路径（含新文件）。解释架构时多用比喻。
- **记忆库由 Claude 维护**：对话中自己总结规律，**用户说「整理 memory base」时统一写进 memory/**；用户明确要求记下某件事（比如「放进待定事项」）时当场写。对话很长、下一步又是大改动时，主动建议开新对话，并先把交接内容写进 `memory/待定事项/`（11-22 的 `06_Boss第4阶段_交接.md` 就是这么来的）。
- **玩家和 Boss 的同类功能分开写，不共用代码**（11-21 用户要求，例：玩家激光 `LaserSpecial` 和 Boss 的 `BAE_LaserAttacker` 各写各的），方便分清哪部分是谁的。通用的编辑器工具可以参考，但不跨过去改 Boss 文件。
- **配置重复 → 直接报错、都不生效**，不要"以前面的为准"（用户原话：到时候我自己调）。节拍总表同一招拖进两行、双蓄配方等级总和重复都按这条处理。
- **新参数的默认值要保证现有手感不变**；用 `-1` 表示"跟随 / 自动"（比如时间填 -1 = 跟动画事件走，渐变时长 -1 = 跟起蓄时间）。
- **参数填"结果"而不是"手段"**：高度、距离、时长，而不是力、速度（冲刺 / 滑铲、跳跃都已经这样改了）。
- **Inspector 保持简洁**：按招式类型 / 开关隐藏用不上的栏位（隐藏 ≠ 不生效，要在提示里讲清楚）。
- 用户会问"业界一般怎么做"，回答时给出几种做法的对比和推荐理由。

### 11-22 补充的经验（沟通效率）
- **用户是语音输入，常有同音错字**，要按上下文理解，拿不准时复述一句确认。见过的：晋升 / 竞争反应 = 近身反应，进站 = 近战，熊单招 = 出单招，或顿时 = 破盾值，突进站 = 突进斩，解锁（套路的最后一个招式解锁）= 结束。
- **要用户拍板的设计问题：每一项都附上 Claude 的推荐和理由**，用户同意推荐时只回「OK」就行，只需说出例外。一次最多问 3～4 个，按影响大小排序。
- **回答「现在的代码是怎么做的」之前先读代码**，不凭文档或记忆。11-22 就因为凭记忆说错过一次（说意图距离传送在套路里等于原地不动，其实已经会落到下一步的理想距离），读了代码才更正。用户对现状的印象也可能是旧的（例如以为「玩家一移动，抽好的卡就全部作废」），要用代码事实去对齐。
- **大功能拆成能单独测的小阶段**（11-22：0 / 1 / 1.5 / 2 / 3 / 4a / 4b），一个阶段改完、用户测过说没问题再进下一个。每阶段收尾给 3～5 条具体的测试步骤。
- **用户中途「顺便问一嘴」**：直接回答，不动文件；需要改的话先说明，等确认。
- **在要改的文件里顺手发现的老问题**可以一起修，但要在说明里单独点出来（例：11-22 修了位移卡没填理想距离时 Boss 先往远处走 49.5 格）；不在这次改动范围内的只报告、不改。
- **用户想要的控制方式**：手感上会给玩家造成负担的决定（冲不冲刺、要不要同时放招），用户要自己在套路里逐步配置，不交给 AI 随机。常用的配置模式是「卡上放默认值 + 套路步骤可以覆盖（跟随卡 / 自己选）」。
- **同一功能有两套近似配置时主动指出、建议合并**（11-22：「接下一步的时机」「为下一招靠位」「脱手释放」三合一）。删掉旧参数会让已配好的值作废，要先说清楚哪些资产要重配。
- **对话里的说明要把「层 / 状态」这类抽象概念说具体**：用「谁在控制 Boss 的脚」「打断打到谁」「子弹从哪发出来」这种可观察的效果来解释。11-22 用户就是在这个点上和 Claude 理解不一致（以为脱手后的弹幕留在原地）。
- **以开发为主，不写正式文档**（11-22 用户原话：现在只有我们两个在做，目的是开发游戏）。规格、术语、交接都由 Claude 记在 memory 里，不要求用户写设计文档。
- **先把系统做出来，再在玩的过程中调数值**（用户的开发方式，原型期业界也这么做）。不要求提前定具体数字；调某个东西之前，用一句话说清「这次想要什么感觉」（例如「这个套路打完玩家要有一次反击机会」），作为判断「调好了没有」的标准。用户没说时，Claude 可以问一句。
- **用户说「配了却不触发 / 不生效」时，先查配置再怀疑代码**：读场景 / 资产核对（提醒先保存），请用户展开新加的列表条目看数值（Unity 新加条目可能是 0，见 05）。11-22 两次都是配置问题（冷却 100、Max Distance 0）。但讲原因前要先读代码，不要只凭推测说「是距离不够」。
- **路线里没定义的阶段号**（例如 11-22 用户说「继续做 5 阶段」）：先对照 memory 里的路线，复述候选让用户确认。
- **大的面板 / 数据结构改动之前，先专门聊一次架构、不写代码**：Claude 先把现有的卡、套路步骤参数、Boss 身上的参数列成表，和用户一起定「每个参数属于哪一级：卡上 / 套路步骤上 / Boss 身上」，再动手。之后每加一个新参数，先对一下它属于哪一级。

### 文件写回的流程（这个会话环境下）
- 没有可用的 device shell：用 `device_stage_files` 读 → 在工作区改 → 放到 `/mnt/user-data/outputs/` → **等 15～20 秒**再 `device_commit_files`（带 expectedMtimeMs）→ **再 stage 一次逐字比对**。
- **11-21 踩过坑**：改完马上写回，写回工具读到的是还没同步的旧副本，结果把改动前的内容（还变成了 LF 换行）写回了用户电脑。所以一定要等、一定要核对。
- 保持原文件格式，改之前先用脚本查一遍（BOM、CRLF、结尾有没有换行）：玩家脚本基本是 **UTF-8 无 BOM + CRLF**；**Boss 脚本多数有 BOM**（`BossRoutine.cs`、Boss 的 Editor 脚本没有）；`BossController.cs`、`BossCombatState.cs`、`IBossActionExecutor.cs` 结尾没有换行。新文件用无 BOM + CRLF。
- 用户 git 提交后，文件的修改时间会整体变（内容不变），写回会被 mtime 检查拒绝：重新 stage、逐字比对内容没变，再用新的 mtime 写回。
- **读不到深层文件**：读文件的工具（staging）最多只能读到连接文件夹往下 **7 层**目录里的文件，这是工具本身的限制，和权限无关（列目录能看到、但读不了）。连接的是项目根目录 `D:\Unity project\Flan`，所以 `Assets/Scripts/Player_V0.3/1_Config/P_Combonodes/super/Skills/Lasers/` 里的文件（第 8 层）读不到。解决办法：请用户在桌面端额外连接一个更深的文件夹（比如 `P_Combonodes`），或者把文件挪浅一层；不行就看截图。11-21 用户说读不到就算了。
- 没有 Unity，只能做语法检查（tree-sitter-c-sharp），**每次都要提醒用户打开 Unity 看 Console**。
- memory 文件的格式：`01～05` 是 UTF-8 无 BOM + CRLF；`待定事项/` 下是无 BOM + LF。
