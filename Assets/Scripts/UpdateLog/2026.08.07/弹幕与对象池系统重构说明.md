# 弹幕与对象池系统重构说明

> 面向新接手本模块的开发者。按「解决了什么问题」组织，每个问题下注明改了哪些文件。
> 🆕 = 新建文件　✏️ = 修改文件　❌ = 删除

---

## 一、池对象可能被同时借出两份（数据竞争）

### 问题
`ObjectPoolManager.Recycle()` 原先没有任何「这个对象是不是已经在池里了」的检查。

想象一颗子弹在同一帧里既飞出了屏幕（`Update` 触发回收），又撞到了玩家（`OnTriggerEnter2D` 触发回收）——队列里就躺了**两份同一个 GameObject**。之后两个不同的发射器各借一次，拿到的是同一颗子弹，后一个的 `Setup()` 会覆盖前一个。

表现是「子弹莫名其妙少了 / 方向不对」，且依赖同帧竞态，几乎无法复现。

### 改动
- 🆕 `Core/ObjectPool/PooledObject.cs`
  新增 `IsInPool` 标记，回收时置 true、借出时置 false。
- ✏️ `Core/ObjectPool/ObjectPoolManager.cs`
  `Recycle()` 开头判断 `if (po.IsInPool) return;` —— 重复回收变成幂等的空操作。

## 二、池 key 靠手写字符串，写错就静默泄漏

### 问题
回收时要手动传 key：`Recycle("EnemyBullet", gameObject)`。

而发射器那边用的是可配置的 `[SerializeField] projectileKey`。**两份真相**：在 Inspector 里改了 key，子弹就再也回不了正确的池。更糟的是原代码里 `if (!pool.ContainsKey(key)) return;` —— 直接返回，对象既不失活也不入池，就这么活着飘在场景里，**零报错**。

### 改动
- 🆕 `Core/ObjectPool/PooledObject.cs`
  对象自己记住 `PoolKey`，由池在创建实例时写入。
- ✏️ `Core/ObjectPool/ObjectPoolManager.cs`
  `Recycle(GameObject)` 改为单参数签名，调用方不再传 key。
  旧的双参版本保留为 `[Obsolete]` 转发，方便渐进迁移。
  key 找不到时改为 `Debug.LogError`，不再静默 return。
- ✏️ `Items/Bullets/Enemy_Projectile.cs`
  回收调用改为 `ObjectPoolManager.Instance?.Recycle(gameObject)`。

**规范**：以后任何池化对象归还，一律 `Recycle(gameObject)`，不要传 key。

## 三、借还路径上的 GC 分配

### 问题
`GetComponents<IPoolable>()` **每次调用都会 new 一个数组**。借一次、还一次就是两次分配，同屏几百发子弹持续跑，这是实打实的 GC 压力——正好撞在「彻底消灭 GC 卡顿」这条红线上。

另外 `SpawnProjectile()` 里残留了一行调试日志：
```csharp
Debug.Log($"objpool: {ObjectPoolManager.Instance == null}");
```
Rotation 形态 0.05 秒一发，每次都分配一个新 string 并捕获堆栈。这是当时全项目最贵的一行代码。

### 改动
- 🆕 `Core/ObjectPool/PooledObject.cs`
  首次访问时缓存 `IPoolable[]`，之后借还零分配。
- ✏️ `Core/ObjectPool/ObjectPoolManager.cs`
  借还改用 `po.Poolables`，并用 `for` 循环替代 `foreach`。
- ✏️ `Enemies/Boss/Execution/Bullet/BossBulletEmitter.cs`
  删除调试日志，改为 `if (bullet == null) return null;` 的正经空检查。

## 四、单例初始化时序 + 一个 Unity 陷阱

### 问题
1. 池的预热写在 `Start()` 里。任何在自己 `Start()` 中调用 `Get()` 的组件都可能拿到 null——取决于脚本执行顺序，编辑器里可能一年不出现，换平台打包就翻车。
2. **更隐蔽的陷阱**：`Singleton<T>.Awake()` 原先是 `private`。Unity 的消息派发只调用「最派生类型」上找到的那一个 `Awake`，所以派生类一旦声明自己的 `Awake`，基类那个就被隐藏、永远不执行，`Instance` 保持 null，整个单例静默失效。

### 改动
- ✏️ `Core/Singleton/Singleton.cs`
  `Awake` 改为 `protected virtual`，并新增 `OnDestroy` 清空静态引用（应对关闭 Domain Reload 的情况）。
- ✏️ `Core/ObjectPool/ObjectPoolManager.cs`
  预热移入 `override Awake()`，并加 `[DefaultExecutionOrder(-1000)]` 双保险。

**规范**：以后写单例派生类，`Awake` 必须 `protected override` 并调用 `base.Awake()`。

## 五、阵型子弹的永久泄漏（本次最严重的问题）

### 问题
阵型子弹是池化对象，且被 `SetParent` 挂在阵眼（Formation Parent）之下。一旦阵眼被 `Destroy`——Boss 阵亡、关卡重载、或任何误写的销毁逻辑——**这些子弹会作为子物体被连带销毁**：不走 `Recycle`、不回队列、不报错。池被一次性抽干一整个阵型的量，且永不恢复。

另外有个已废弃的 `FormationBullet` 类，`OnTriggerEnter2D` 里直接 `Destroy(gameObject)`，同样绕过了池。它当时已经是 0 引用的死代码。

### 改动
- 🆕 `Enemies/Boss/Execution/Bullet/FormationCore.cs`
  显式的阵眼类。职责边界：**只管生命周期，绝不参与伤害判定**。
  - `Register()` 登记每颗子弹
  - `Update()` 中子弹掉光 → 收摊；超过 `maxLifeTime` → 强制收摊（防止阵型停在屏幕内、越界回收永不触发）
  - `OnDestroy()` 兜底：被外部直接销毁时，先把所有池化子弹归还再走
- ✏️ `Enemies/Boss/Execution/Bullet/BossBulletEmitter.cs`
  `SpawnSquareBurst()` 与 `CreateFormationParent()` 建阵眼时挂上 `FormationCore` 并逐颗 `Register()`。
  `FormationBase.Update()` 里的自毁判定移除，交给 `FormationCore`。
- ❌ `FormationBullet` 类（原在 `BossBulletEmitter.cs` 底部）
  删除。其中唯一有价值的友军免伤逻辑（`CompareTag("Enemy")`）并入 `Enemy_Projectile`。

**规范**：任何把池化对象挂到某个父物体下的做法，父物体必须能保证销毁前先归还子物体。

## 六、敌我伤害通路不对称

### 问题
两条完全独立的路：

| 方向 | 调用 | 带 DamageType？ |
|---|---|---|
| 玩家 → 敌人 | `EntityBase.TakeDamage(damage, DamageType)` | ✅ |
| 敌人 → 玩家 | `playerState.health.TakeDamage(damage, knockbackVector, runner)` | ❌ |

Boss 的护盾按近战/远程分别结算，玩家侧却完全没有这个维度——以后要做「玩家护盾只挡远程」「弹反只对近战生效」，就得把整条调用链推倒重签。

**另一个发现**：子弹里那句 `new Vector2(Mathf.Sign(relativeX) * 8f, 5f)` 中的 `8f` 和 `5f` **从未生效**。`HitState` 只取了 x 的符号，力度一直来自 `PlayerStateMachine.hitKnockbackForce`。所以那是两个误导性的死数字。

### 改动
- 🆕 `Core/Combat/DamageInfo.cs`
  `DamageInfo` 载荷结构体（`readonly struct`，用 `in` 传递，无堆分配）+ `IDamageable` 接口。
  载荷含 `amount` / `type` / `sourcePosition` / `instigator`。
  **刻意不含击退力度**：攻击方只说「我从哪来」，方向与力度归受击方决定。
- ✏️ `Enemies/Boss/EntityBase.cs`
  实现 `IDamageable`；`TakeDamage(in DamageInfo)` 成为唯一 virtual 核心；
  旧签名降级为非虚的 `[Obsolete]` 转发。
- ✏️ `Player_V0.1/PlayerState.cs`
  实现 `IDamageable`，在此处由 `sourcePosition` 推算击退方向。
- ✏️ `Enemies/Boss/BossLogic/BossController.cs`
  `override` 改为新签名（转发逻辑一字未动，护盾/破甲/防反传送完全保留）。
- ✏️ `Items/Bullets/Enemy_Projectile.cs`
- ✏️ `Items/Bullets/Player_Projectile.cs`
- ✏️ `Items/Bullets/Player_HomingProjectile.cs`
- ✏️ `Player_V0.1/Combo/PlayerHitDetection.cs`
- ✏️ `Player_V0.1/Player.cs`
  以上五处调用方改为传 `DamageInfo`。

**规范**：新增任何伤害来源，一律构造 `DamageInfo` 调用 `IDamageable.TakeDamage`。
需要新的伤害维度（元素、破防等）时，加字段到 `DamageInfo`，不要新开重载。

## 七、运行时增删组件

### 问题
`BulletAcceleration` 原先是用完就拆：发射时 `AddComponent`，回收时 `Destroy(ba)`。

1. `AddComponent` / `Destroy(Component)` 都是 native 侧的结构性操作，会分配托管包装对象并重排组件数组。Rotation 形态每秒 20 次装拆。
2. `Destroy(Component)` **延迟到帧末执行**。子弹回收后若在同一帧被重新借出，拿到的是一颗还挂着旧加速器、且该组件即将消失的**脏子弹**。
3. 越权：由 `Enemy_Projectile` 负责清理别人的组件。

### 改动
- 🆕 `Items/Bullets/BulletAcceleration.cs`
  从 `BossBulletEmitter.cs` 内部**拆为独立文件**（必须——Unity 只允许拖拽与文件同名的 MonoBehaviour，而它现在需要常驻在预制体上）。
  改为常驻组件 + `Configure()` 开关，实现 `IPoolable` 自行重置。
  **关键**：`baseSpeed` 快照从 `Start()` 移到 `Configure()`。`Start()` 一生只执行一次，常驻化后第二次借出不会再跑，快照会永远停在第一发子弹的速度上。
- ✏️ `Enemies/Boss/Execution/Bullet/BossBulletEmitter.cs`
  `AddComponent` 改为 `GetComponent(...).Configure(rate, coef)`。
  ⚠️ 必须保持在 `projScript.speed = speedOverride;` **之后**，否则快照取到上一发的速度。
- ✏️ `Items/Bullets/Enemy_Projectile.cs`
  删除 `OnDespawn` 里的 `Destroy(ba)`。

**规范**：高频实体上的组件一律常驻 + 开关控制，禁止运行时 `AddComponent` / `Destroy(Component)`。

## 八、每颗子弹每帧一次矩阵变换

### 问题
```csharp
Vector3 vp = Camera.main.WorldToViewportPoint(transform.position);
```
`WorldToViewportPoint` 内部要走「世界 → 相机 → 投影 → 视口」的完整矩阵变换链。同屏 300 发就是每帧 300 次矩阵运算——而这 300 次算出来的相机边界完全相同，纯属重复劳动。

注意：这里贵的是 **CPU 时间**，不是内存——该方法不产生堆分配。

### 改动
- 🆕 `Core/ScreenBounds.cs`
  静态类，每帧只计算一次相机边界并缓存（按 `Time.frameCount` 自动失效）。
  子弹只需 4 次浮点比较。
  **`margin` 保持原有的「屏幕比例」语义**（0.5 = 上下左右各外扩半个屏幕），Inspector 数值无需改动——若误改成世界单位，0.5 会骤缩成半格，绕圈的阵型子弹会被提前回收。
- ✏️ `Items/Bullets/Enemy_Projectile.cs`
  `Update()` 改为 `if (ScreenBounds.IsOutside(transform.position, margin))`。

## 九、回收时的状态残留

### 问题
`OnDespawn()` 里 `transform.localScale = new Vector3(0.5f, 0.5f, 1)` —— 从预制体抄来的魔法数字，改了预制体这里就悄悄失配。
另外 `rotation`、`angularVelocity`、`speed`（会被加速器持续改写）都没重置。

### 改动
- ✏️ `Items/Bullets/Enemy_Projectile.cs`
  `Awake()` 中拍下 `originalScale` / `originalSpeed` 快照，`OnDespawn()` 逐一还原。
  同时移除了重复的 `SetParent`（原先池和子弹各做一次，每次触发一遍层级 dirty），统一交给 `Recycle`。

## ⚠️ 编辑器侧的必做操作

代码之外还有一步，**漏了加速弹会完全失效**：

> 把 `BulletAcceleration` 组件手动挂到子弹预制体（`EnemyBullet`）上。

它不再由 `AddComponent` 动态创建，必须常驻。挂上后 Inspector 里看不到可调字段——这是对的，参数全部由 `Configure()` 运行时注入，避免「Inspector 配一份、代码传一份」的双份真相。

## 遗留项

以下问题已确认存在但本轮未处理：

1. **`Player_Projectile` / `Player_HomingProjectile` 尚未接入对象池**
   仍在用 `Instantiate` + `Destroy(gameObject, lifeTime)` + `OnBecameInvisible`。敌方子弹已池化，玩家子弹是漏网的。
2. **`Enemy_Projectile` 命中玩家后不回收**（穿透弹）
   保持了原有行为。若要改成命中即回收，需配套记录「已命中目标」以防重复扣血。
3. **`Enemy_Projectile.lifeTime` 是死字段**
   目前只有「飞出屏幕」一条回收路径。阵型子弹的超时兜底现由 `FormationCore.maxLifeTime` 承担。
4. **每颗子弹一个 `Update()`**
   Unity 每个 MonoBehaviour 的 `Update` 都有一次 native→managed 跨界调用开销。弹幕密度真正上来后，可改为由一个 Manager 统一遍历。
5. **`CameraSequenceController` 里的 `player.GetComponent<MonoBehaviour>()`**
   返回该物体上第一个 MonoBehaviour，谁挂在最前面就禁谁——会随 Inspector 顺序漂移的真 bug。
6. **逐招式的击退力度**
   目前所有受击共用 `PlayerStateMachine.hitKnockbackForce`。若要做「重击击退更远」，需扩展 `DamageInfo` 并改动 `OnPlayerHit` 事件签名。
